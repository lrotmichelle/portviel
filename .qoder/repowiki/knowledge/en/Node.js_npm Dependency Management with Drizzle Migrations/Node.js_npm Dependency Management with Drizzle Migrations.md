## System/Approach

This Next.js application uses **npm** as its package manager, declared via `package.json` at the repository root. Dependencies are pinned using caret (`^`) ranges in both `dependencies` and `devDependencies`, and a `package-lock.json` lockfile is present to ensure reproducible installs. The project enforces a minimum Node.js runtime of `>=20.19.0` and npm `>=10.0.0` through the `engines` field.

The build/deploy pipeline is driven by **Nixpacks** (`.nixpacks.toml`), which provisions `nodejs_20` and `npm-9_x` for the runtime environment. There is no custom CI script — deployment relies on Nixpacks' standard `npm install` / `next build` flow.

## Key Files

- `package.json` — declares all runtime and dev dependencies, scripts, and engine constraints.
- `package-lock.json` — lockfile pinning exact resolved versions.
- `.nixpacks.toml` — specifies the Node.js/npm versions used during builds.
- `drizzle.config.ts` — configures Drizzle ORM migrations against PostgreSQL, pointing schema to `./src/db/schema.ts` and outputting SQL migrations into `./drizzle/`.
- `scripts/run-migrations.mjs` — Node.js migration runner executed before every `dev`, `build`, and `start` command; it loads `DATABASE_URL` from process env or falls back to `local.env`, then runs Drizzle migrations against the database.
- `drizzle/0000_init.sql` + `drizzle/meta/_journal.json` — generated migration files and journal tracking applied migrations.
- `local.env` — local-only database connection string (not committed to version control).

## Architecture & Conventions

- **Single manifest**: All third-party packages are declared centrally in `package.json`; there is no monorepo, workspaces, or sub-package manifests.
- **Versioning strategy**: Caret ranges (`^x.y.z`) are used across the board, allowing minor/patch updates while guarding against breaking changes. No explicit dependency update policy is codified beyond this convention.
- **Runtime vs. dev split**: Runtime dependencies (Next.js, React, Drizzle ORM, PostgreSQL driver, Radix UI primitives, Tailwind utilities) are separated from dev tooling (TypeScript, ESLint, PostCSS plugin, type definitions).
- **Database layer**: Drizzle ORM is configured declaratively via `drizzle.config.ts`. Schema lives in `src/db/schema.ts`, and migrations are generated into `drizzle/` and auto-applied at startup via the pre-run script. This makes the DB schema a first-class managed dependency alongside npm packages.
- **Environment-driven configuration**: Database connectivity is injected via `DATABASE_URL` (process env or `local.env`); no secrets are checked into source control.

## Conventions & Constraints

- **Engine pinning**: The project requires Node `>=20.19.0` and npm `>=10.0.0` (enforced by the `engines` field in `package.json`).
- **Pre-start migration**: Every `dev`, `build`, and `start` invocation runs `node scripts/run-migrations.mjs` first, ensuring the database schema stays in sync with the codebase.
- **Migration immutability**: Existing migrations under `drizzle/` must not be edited; new changes are added as new numbered SQL files generated by Drizzle Kit.
- **Dev-mode tolerance**: When `NODE_ENV=development` and the database is unreachable, the migration script logs a warning and exits successfully so the dev server can continue without a live DB.
- **No vendoring**: Dependencies are installed from the public npm registry; there is no `vendor/`, private registry URL, or proxy configuration in the repo.
- **Lockfile usage**: `package-lock.json` is present and should be kept in sync with `package.json` to guarantee deterministic installs across environments.
